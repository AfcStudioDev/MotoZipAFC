# Развёртывание в Docker

## Архитектура

```
                 ┌────────────────────────┐
  браузер  ───▶  │  caddy                 │  порт наружу: 80, 443
                 │  TLS-терминация,       │  (единственный сервис, торчащий наружу)
                 │  автопродление         │
                 │  сертификата           │
                 └───────────┬────────────┘
                             │ внутренняя docker-сеть
                 ┌───────────▼────────────┐
                 │  frontend (nginx)      │  наружу не публикуется
                 │  Angular + reverse     │
                 │  proxy /api, /ZipPhotos│
                 └───────────┬────────────┘
                             │
                 ┌───────────▼────────────┐
                 │  api (ASP.NET Core)    │  наружу не публикуется
                 └───────────┬────────────┘
                             │
                 ┌───────────▼────────────┐
                 │  postgres              │  наружу не публикуется
                 └────────────────────────┘
```

Фронтенд и бэкенд работают с одного origin (nginx проксирует `/api/*` и `/ZipPhotos/*` на контейнер бэкенда) — благодаря этому браузеру не нужен CORS. Caddy — единственная точка входа снаружи и всегда поднимает HTTPS с редиректом с 80 на 443, независимо от того, реальный домен указан в `.env` или `localhost` (подробности — в разделе про HTTPS ниже). Бэкенд, база данных и nginx-контейнер фронтенда наружу не публикуются вообще.

## Предварительные требования

- Docker Engine + Docker Compose v2 (`docker compose version`).

## Первый запуск

1. Скопируйте шаблон настроек и заполните его:

   ```bash
   cp .env.example .env
   ```

   Обязательно замените: `POSTGRES_PASSWORD`, `JWT_KEY` (минимум 32 символа), `SEED_ADMIN_PASSWORD`, `SEED_SENDER_PASSWORD`, `SEED_REGISTRAR_PASSWORD`. Без них контейнеры откажутся стартовать — `docker compose` явно укажет, какой переменной не хватает.

   `DOMAIN` и `PUBLIC_URL` по умолчанию — `localhost`, для локальной проверки без домена. Для реального сервера см. раздел «HTTPS на реальном домене» ниже.

2. Соберите образы и поднимите стек:

   ```bash
   docker compose up -d --build
   ```

3. При первом старте бэкенд сам применит миграции (Code First) и создаст справочники операций, администратора и демо-каталог — ничего вручную выполнять не нужно.

4. Откройте `https://localhost` (или `DOMAIN` из `.env`). Для `localhost`/IP браузер один раз спросит, доверять ли сертификату (Caddy подписывает его собственным локальным CA, раз настоящего домена нет) — это ожидаемо, соглашайтесь. Войдите под `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` из `.env`.

## HTTPS на реальном домене

За TLS отвечает Caddy — сертификат Let's Encrypt получает и продлевает сам, никакого certbot и ручных cron-задач не нужно.

**Предварительные условия:**
- домен уже указывает A-записью на публичный IP сервера;
- у хостинга/файрвола открыты порты **80 и 443** (оба — 80 нужен не только для редиректа, но и для самой проверки владения доменом при выпуске сертификата).

**Про `www`:** чтобы Caddy обслуживал и `www`, перечислите оба хоста в `CADDY_SITE_ADDRESS`:

```dotenv
CADDY_SITE_ADDRESS=motoparts.example.com, www.motoparts.example.com
```

Запросы на `www` уйдут постоянным редиректом (301) на канонический адрес из `DOMAIN`. Так сайт работает с одного origin — иначе `PUBLIC_URL`, ссылки в письмах сброса пароля и redirect URI у OAuth и оплаты расходились бы с адресом в браузере.

Добавляйте `www` только если у домена есть соответствующая A-запись, иначе Caddy будет впустую запрашивать для него сертификат.

## Доступ по IP из локальной сети

Если нужно открыть сайт с другого устройства в сети по IP-адресу машины, **HTTPS работать не будет**: Let's Encrypt не выдаёт сертификаты на IP-адреса, а собственный CA Caddy не вызывает доверия на других устройствах. Причём Caddy обслуживает только те адреса, что перечислены в `CADDY_SITE_ADDRESS` — при обращении по IP, которого там нет, сертификата не находится вовсе и соединение обрывается с ошибкой вида `SSL_ERROR_INTERNAL_ERROR_ALERT` (её нельзя «принять» в браузере, в отличие от обычного предупреждения о недоверенном сертификате).

Для такого сценария отдавайте обычный HTTP — префикс `http://` отключает TLS для этого адреса:

```dotenv
DOMAIN=192.168.1.50
PUBLIC_URL=http://192.168.1.50
CADDY_SITE_ADDRESS=http://192.168.1.50
```

Годится для внутреннего тестирования; для публикации в интернет используйте домен.

**Порядок действий:**

1. В `.env` укажите домен вместо `localhost` — в обеих переменных сразу, они должны указывать на один и тот же хост:

   ```dotenv
   DOMAIN=motoparts.example.com
   PUBLIC_URL=https://motoparts.example.com
   ```

2. Перезапустите стек:

   ```bash
   docker compose up -d --build
   ```

3. Откройте `https://motoparts.example.com` — сертификат Caddy получит автоматически при первом обращении (может занять несколько секунд). HTTP на 80-м порту сам редиректит на HTTPS — дополнительно ничего настраивать не нужно.

**Важно про volume `caddy-data`:** в нём лежит выпущенный сертификат. Не удаляйте его без необходимости (`docker compose down -v` стирает и его) — Let's Encrypt ограничивает выпуск 5 сертификатами на домен в неделю, и при частом «переполучении» с нуля можно упереться в этот лимит.

**Проверить статус сертификата:**

```bash
docker compose logs caddy | grep -i certificate
```

## Обновление после изменений в коде

```bash
docker compose up -d --build
```

Пересоберёт только то, что изменилось, применит новые миграции при старте `api`, данные в volume-ах (БД, фото) не тронет.

## Изменение настроек без правки кода

Поменяйте нужную переменную в `.env` и перезапустите:

```bash
docker compose up -d
```

Пересборка образов не нужна — все настройки (кроме самого адреса API у фронтенда, см. ниже) читаются из переменных окружения при старте контейнера.

Адрес API (`API_URL`) — особый случай: это часть **рантайм**-конфигурации фронтенда (`config.json`), которую генерирует entrypoint-скрипт nginx-контейнера из `.env` при каждом старте — то есть тоже без пересборки, но требует пересоздания контейнера `frontend` (`docker compose up -d frontend`), если менялось только это значение.

## Данные, которые переживают пересоздание контейнеров

| Volume | Что хранит |
|---|---|
| `pgdata` | база PostgreSQL |
| `zip-photos` | загруженные фотографии запчастей (`/app/wwwroot/ZipPhotos` внутри контейнера `api`) |
| `caddy-data` | сертификат Let's Encrypt (см. предупреждение про лимит выпуска выше) |
| `caddy-config` | служебное состояние Caddy |

`docker compose down` их не трогает. Удалить безвозвратно — `docker compose down -v` (осторожно, это стирает БД, фото и сертификат).

## Резервное копирование БД

```bash
docker compose exec postgres pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" > backup.sql
```

Восстановление:

```bash
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" < backup.sql
```

## Логи

```bash
docker compose logs -f api
docker compose logs -f frontend
docker compose logs -f postgres
docker compose logs -f caddy
```

## Диагностика

- **Контейнер `api` не стартует, ошибка в логе про переменную окружения** — не заполнено обязательное значение в `.env` (см. список в шаге 1).
- **Открывается пустая страница / 502 на `/api/...`** — бэкенд ещё не поднялся или упал; смотрите `docker compose logs api`.
- **Фото не загружаются (413 Request Entity Too Large)** — лимит `client_max_body_size` в `frontend/nginx.conf` (по умолчанию 30 МБ на все 3 фото), увеличьте при необходимости и пересоберите фронтенд-образ.
- **Меняли `.env`, но браузер продолжает бить в старый API-адрес** — жёстко закешировался `config.json` в браузере; сделайте hard-refresh (Ctrl+F5). Сам nginx его не кеширует (`Cache-Control: no-store`).
- **Сертификат не выпускается / `caddy` перезапускается в цикле** — почти всегда: домен ещё не резолвится на IP сервера, либо порт 80/443 закрыт файрволом/хостингом. Проверьте `docker compose logs caddy`.
- **`curl`/скрипты ругаются на сертификат при обращении к `localhost`** — это самоподписанный локальный CA Caddy, не настоящий Let's Encrypt (см. «HTTPS на реальном домене»). Для разовой проверки: `curl -k`. Для постоянного доверия локально: `docker compose exec caddy cat /data/caddy/pki/authorities/local/root.crt` и добавить сертификат в доверенные корневые ОС/браузера.

## Безопасность перед публикацией в интернет

- `.env` не должен попасть в git (уже в `.gitignore`) и не должен лежать рядом с публично доступными файлами на сервере.
- Смените дефолтные `SEED_*` пароли и `JWT_KEY` — значения из `.env.example` предназначены только как подсказка формата.
- Порты `postgres` (5432), `api` (8080) и `frontend` (80, внутренний) в docker-compose.yml не публикуются на хост — это осознанное решение, наружу торчит только `caddy`. Не раскомментируйте `ports:` у `postgres` без реальной необходимости.
- HTTPS на реальном домене — см. отдельный раздел выше, там же предупреждение про лимит Let's Encrypt.
